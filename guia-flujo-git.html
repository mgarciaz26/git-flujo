00Empieza aquí: de cero a funcionando

Si no sabes nada de Git ni de skills, sigue estos pasos en orden, sin saltarte ninguno. Al final tendrás todo funcionando.

  1. Reúne lo necesario (pídelo al encargado si te falta algo):
    • Git instalado → comprueba con git --version en la terminal.
    • GitHub CLI → comprueba con gh --version; si falta, instálalo y corre gh auth login.
    • Claude con modelo Sonnet (comando /model para elegirlo).
    • La URL del repo del ERP y tu usuario de GitHub con acceso.
    Éxito: los dos comandos de versión responden sin error.
  2. Clona el repo y entra a la carpeta: 
    git clone <url-del-repo>
cd <carpeta-del-repo>
    Éxito: ves los archivos del ERP listando la carpeta.
  3. Crea los skills (elige UNA opción):
    • A · Copiar: copia la carpeta .claude/ del git-flujo.zip a la raíz del repo.
    • B · Pegar en terminal: copia TODO el crear-skills.ps1, pégalo en PowerShell en la raíz y pulsa Enter.
    • C · Regenerar: usa los prompts de la sección 08 para crearlos desde cero.
    Éxito: existe .claude/skills/nueva-tarea/SKILL.md (y los otros 4).
  4. Abre Claude en la carpeta y verifica: escribe hola, ¿qué skills tienes disponibles? → debe listar los 5. Luego prueba sin miedo: nueva tarea para el requerimiento ERP-999 prueba → debe crear feature/erp-999-prueba pidiendo confirmación.
  5. Crea las ramas (admin, una sola vez): 
    git checkout -b develop
git push -u origin develop
git checkout -b qa
git push -u origin qa
  6. Aplica la protección (admin, una sola vez): sigue la sección 03 para bloquear main y qa. Éxito: si un desarrollador intenta pushear a main, GitHub lo rechaza por rama protegida.
¿Cómo sé que todo funcionó? Marca esta lista: rama de prueba creada · commit con código TGE-PROD · PR con etiqueta requerimiento/soporte · main bloqueada para devs. Si algo falla, vuelve al paso indicado: casi siempre es gh sin login o Claude abierto fuera de la carpeta del repo.

01El flujo y sus reglas

Cada cambio nace en su propia rama feature/ (requerimiento) o fix/ (soporte), lleva el código de su documento de pase como título del commit y solo sube de nivel pasando por cada regla. Este es el mapa completo:

Regla de oro Nadie sube ni fusiona directo en main ni en qa: lo bloquea GitHub. Todo viaja por Pull Request y Claude siempre te mostrará el recorrido desde … → hacia … y te pedirá confirmación antes de ejecutar. El bloqueo se configura como indica la sección 03.
El código es la trazabilidad Cada pase tiene su documento con un código correlativo (TGE-PROD-20260907-000004) generado ANTES del commit por el aplicativo de documentación. Ese código es el título del commit y un tag sobre él: viaja con el commit al fusionarlo a develop, qa y main, así que en cualquier rama el código resuelve a los mismos archivos (git show <codigo>).

03Cómo se bloquea main y qa

Lo hace el admin del repositorio, una sola vez. Esta es la configuración que impide técnicamente que un desarrollador publique en main.

  1. Abrir las reglas: en el repositorio de GitHub ir a Settings → Branches → Add branch protection rule.
  2. Regla para main: en "Branch name pattern" escribir main y activar:
    • Require a pull request before merging (nadie sube directo).
    • Restrict who can push to matching branches y agregar como autorizados a los 4 gestores: Wilmer Moscol, Marlon García, Jorge Salas y Víctor Roldán (se agregan por su usuario de GitHub).
    • Enforce admins (ni siquiera un admin salta la regla).
    Guardar con Create.
  3. Regla para qa: repetir lo mismo con pattern qa, autorizando solo al equipo QA: Randy Correa, Luis Castro y Ronald Salazar.
  4. Regla para develop: pattern develop, activar solo Require a pull request before merging (sin lista de autorizados, para que cualquier desarrollador pueda fusionar ahí).

Efecto: qué le pasa a un desarrollador

Si intenta…GitHub responde
git push directo a main Rechazado: rama protegida.
Abrir un Pull Request hacia main Puede crearlo, pero solo un Gestor puede fusionarlo.
git push o fusionar en qa Rechazado: solo el equipo QA.
Trabajar en feature/, fix/ y fusionar en develop Permitido: es su espacio de trabajo.

Cómo funcionan las aprobaciones

GitHub no tiene un "rol de aprobador" como tal: combina dos niveles. El permiso del repo (todos tienen Write; sin eso ni siquiera podrían subir sus feature/) y la lista blanca por rama (solo los usuarios de la lista pueden fusionar en main o qa). La lista se configura por persona (su usuario de GitHub) o por equipo.

Basta que UN gestor fusione: cualquiera de los 4 (Wilmer, Marlon, Jorge, Víctor) puede aprobar el release; no se exige que lo aprueben los 4. Un desarrollador puede crear el PR, pero GitHub le bloquea el botón de fusionar. El aprobador no necesita ningún permiso especial: con Write + estar en la lista blanca de main es suficiente.

Variante estricta (opcional, a futuro)

  • Aprobaciones requeridas: exigir 1 visto bueno de otra persona además del gestor que fusiona.
  • CODEOWNERS: archivo que asigna revisores automáticamente según carpetas del repo.
  • Equipos: con organización en GitHub, crea los equipos Gestores y QA y usa el equipo en la regla: cuando entre o salga gente solo tocas el equipo, no las reglas.
Alternativa con comandos En la carpeta github/ van los archivos proteccion-main.json, proteccion-develop.json y proteccion-qa.json con estas mismas reglas, más los comandos en INSTALAR.txt (paso 4, opción B). Hay que reemplazar los usuarios de ejemplo por los usuarios reales de GitHub.

escribir-commit título = código TGE-PROD · crea el tag local

Qué hará, en orden:

  1. Revisa git status y analiza el diff de los formularios cambiados.
  2. Te pide el código del documento de pase (obligatorio): será el título del commit. Si aún no lo tienes, te muestra la lista de archivos para que armes el documento en el aplicativo y vuelvas con el código.
  3. Lee Tipo y Ticket de tu rama (feature/ → requerimiento, fix/ → soporte) y redacta con IA la descripción + lista de archivos.
  4. Propone mensaje y te pide confirmación. Jamás hace push. Tras commitear, crea el tag local con el mismo código (segunda confirmación).
cambios en tu carpeta → commit local con título TGE-PROD-… → tag local (no sube nada)

08Cómo crear un skill desde cero

Un skill no es magia: es un archivo Markdown con instrucciones claras. Si entiendes su anatomía, puedes crear los tuyos y usarlos en cualquier IA.

Anatomía de un SKILL.md

---
name: mi-skill                  # minúsculas con guiones, igual que la carpeta
description: qué hace + ...     # CUÁNDO se usa + palabras gatillo (la IA lee esto)
allowed-tools: Bash(git:*)      # opcional: comandos pre-autorizados
---
# Título del skill
Objetivo, reglas, pasos numerados, formatos y confirmaciones.

La clave es description: la IA la lee para decidir cuándo activar el skill. Incluye los verbos y frases que dirá el usuario ("crear rama", "commit", "ERP-123"). Sin una buena descripción, el skill existe pero nunca se dispara.

Receta en 5 pasos

  1. Define la tarea en una frase: qué entra y qué sale (ej.: "crear la rama feature/fix desde develop y publicarla").
  2. Elige las frases gatillo y ponlas en description (ej.: "nueva tarea", "crear rama", "ERP-123").
  3. Escribe los pasos como órdenes verificables con comandos exactos (no "actualiza develop", sino git checkout develop + git pull origin develop).
  4. Fija formatos y confirmaciones: plantillas de mensajes, rutas "desde → hacia" y la pregunta literal "¿Estás seguro…? (sí / no)" antes de cada acción irreversible.
  5. Prueba y ajusta: abre la IA en el repo, di la frase gatillo y verifica que pida confirmación y muestre la ruta. Si falla, ajusta la descripción o los pasos.

Dónde va según la IA (el contenido es el mismo)

IAUbicación del skill
Claude (proyecto).claude/skills/<nombre>/SKILL.md
Claude (global, todas tus carpetas)~/.claude/skills/<nombre>/SKILL.md

El archivo SKILL.md sigue el mismo estándar abierto: solo cambia la carpeta (proyecto o global). Por eso los 5 skills del paquete funcionan en cualquiera de esas rutas sin reescribirlos.

Plantilla lista para copiar

En el paquete va el archivo SKILL-PLANTILLA.md: cópialo a .claude/skills/<nombre>/SKILL.md, rellena los corchetes con tu tarea y reinicia Claude.

10Errores comunes y cómo salir

Modifiqué sin crear la rama (olvidé nueva-tarea)

No commitees en develop: el skill nueva-tarea te ofrece guardar tus cambios a un lado, crear la rama y devolverlos. A mano sería:

git stash -u
(nueva-tarea: crea la rama)
git stash pop

Push rechazado (ahead/behind)

Tu rama quedó detrás de la remota:

git pull
git push

Quiero "renombrar" un commit con el código

No se puede: los commits publicados son inmutables (cambiar el mensaje genera otro commit). La forma correcta es el tag del pase: git tag TGE-PROD-20260907-000004 sobre ese commit (si aún está solo en tu máquina, usa git tag -f para moverlo; si ya se pusheó, NO lo muevas). De ahora en adelante, commitea con el skill escribir-commit, que pide el código como título y crea el tag solo.

Conflicto de merge

Dos personas tocaron las mismas líneas. Resuelve dejando el código correcto y luego:

git add .
git commit -m "TGE-PROD-20260907-000004" -m "resuelve conflicto"

Commit en la rama equivocada

git checkout feature/erp-101-x
git cherry-pick <hash>

Cambios sueltos y quieres cambiar de rama

git stash
git checkout develop
git stash pop
Prohibido Push o merge directo a main o qa. Si git te dice "protected branch", es lo esperado: abre el PR y que quien deba lo apruebe.

11Ciclo de 6 pasos de cualquier requerimiento o soporte

  1. Empezar. nueva-tarea crea tu rama: feature/ o fix/ desde develop.
  2. Trabajar en el formulario, con la rama activa.
  3. Documentar. Arma el documento en el aplicativo (lee tus cambios sin commitear) y obtén el código TGE-PROD del pase.
  4. Commitear. escribir-commit usa el código como título del commit y crea el tag local.
  5. Entregar. promover pushea rama + tag y crea el PR a develop (y a qa si piden pruebas) con el código en el título.
  6. Publicar. release agrupa los pases en main (Gestor); Pase Producción descarga cada código con publicar, y despliega.

La regla que distingue cada cambio: feature/ = requerimiento y fix/ = soporte. Todo lo demás (commits, PRs, releases) se etiqueta solo. Y siempre, antes de mover algo: Claude te pregunta si estás seguro y te muestra de dónde a dónde viaja.

12Glosario de términos

Todas las palabras usadas en este manual, explicadas en simple y con referencia a dónde se usan.

Conceptos de Git

Pull Request (PR)

Solicitud para fusionar una rama en otra. Es el lugar donde se revisa, se comenta y se aprueba un cambio antes de que entre. Lo crean los skills promover y release. Ver sección 05.

Rama (branch)

Línea de trabajo aislada. Cada requerimiento o soporte vive en su propia rama hasta que se fusiona. Ver sección 01.

Commit

Foto de un conjunto de cambios con un mensaje que lo describe. Es local hasta que haces push. Aquí el título del commit ES el código del documento de pase (ej. TGE-PROD-20260907-000004) y el cuerpo lleva Tipo, Ticket y descripción. Lo crea el skill escribir-commit. Ver sección 05.

Push

Subir tus commits locales al repositorio remoto (GitHub). Sin push, nadie más ve tu trabajo.

Pull

Bajar los cambios del remoto y fusionarlos en tu rama actual. Ej.: git pull en develop antes de crear tu rama.

Fetch

Bajar los cambios del remoto sin fusionarlos: solo actualiza tu copia de referencia para comparar.

Merge (fusión)

Unir una rama dentro de otra. Ej.: fusionar tu feature/ en develop al aprobar el PR.

Conflicto de merge

Ocurre cuando dos personas cambian las mismas líneas. Git marca el archivo y alguien debe elegir el código correcto a mano. Ver sección 10.

Diff

Las diferencias línea por línea entre dos estados (lo que cambiaste vs. lo commiteado). El skill escribir-commit lo analiza para redactar el mensaje.

Stage (área de preparación)

Zona intermedia: con git add eliges qué archivos entrarán en el próximo commit.

Checkout

Cambiarse de rama: git checkout develop. También sirve para crearla con -b.

Stash

Guardar tus cambios sin commitear "a un lado" para cambiar de rama, y recuperarlos después con git stash pop.

Cherry-pick

Traer un commit puntual de otra rama a la actual (útil si commiteaste en la rama equivocada).

origin

Nombre del repositorio remoto (GitHub). origin/develop es "el develop que está en GitHub".

HEAD

El commit donde estás parado ahora mismo. develop..HEAD significa "lo que tu rama tiene y develop aún no".

Tag (etiqueta)

Marca con nombre sobre un commit: aquí es el código del documento de pase, ej. TGE-PROD-20260907-000004 (prefijo + fecha + correlativo: se ordena solo). El skill escribir-commit lo crea en local sobre el commit y promover lo publica junto con la rama; el tag viaja con el commit al fusionarlo a develop, qa y main. publicar descarga por ese código.

Release (conjunto de pases)

Conjunto de pases publicado a producción. Lo prepara el skill release como PR de develop a main agrupando los códigos ya numerados en las tareas (el release no crea código nuevo).

Tipo y Ticket (cuerpo del commit)

Líneas del cuerpo del mensaje que clasifican el cambio: Tipo: requerimiento o Tipo: soporte, y Ticket: ERP-101. Las generan los skills desde la rama (feature/ o fix/); los PRs y el release las leen para clasificar.

Ramas y reglas del ERP

main

Rama de producción: lo que hay aquí es lo que usa el cliente. Solo los Gestores fusionan. Pase Producción descarga desde aquí.

develop

Rama de integración: a donde llegan todos los requerimientos y soportes por PR. Cualquier desarrollador puede fusionar aquí.

qa

Rama de pruebas: lo que el equipo QA va a probar antes del release. Solo QA fusiona aquí.

feature/*

Rama de requerimiento (nueva funcionalidad o mejora). Nace de develop. Ej.: feature/erp-101-ruc-pedido-venta.

fix/*

Rama de soporte (corrección de error). Nace de develop. Ej.: fix/erp-102-arqueo-caja-chica.

Rama protegida

Regla de GitHub que bloquea el push directo y restringe quién puede fusionar PRs en esa rama. Así se impide que un desarrollador publique en main. Ver sección 03.

Ticket (ERP-XXX)

Identificador del requerimiento o soporte. Viaja en el nombre de la rama, en cada commit y en cada PR para rastrear el cambio de punta a punta.

Herramientas

Claude (Sonnet)

Claude con modelo Sonnet, ejecutado en la terminal: analiza tu código, redacta commits y crea los PRs por ti siguiendo los skills. Los skills viven en la carpeta .claude/skills del repo y se cargan solos. Todo este manual asume ese modelo.

Skill

Receta de instrucciones que le dice a Claude cómo hacer una tarea (crear la rama, commitear, promover, release), incluyendo pedirte confirmación.

gh (GitHub CLI)

Programa de terminal para operar GitHub con comandos (crear PRs, verlos, fusionarlos). Los skills lo usan por dentro; se instala una sola vez. Ver INSTALAR.txt.

Documento de pase a producción

Documento del equipo donde cada pase lleva su código correlativo (TGE-PROD-20260907-000004), los archivos y los scripts BD. Se genera en el aplicativo ANTES del commit (lee los cambios sin commitear con git diff --name-only HEAD); el código resultante es el título del commit y su tag. Pase Producción descarga usando ese código, sin necesitar saber de desarrollo.

Visual Studio

Donde escribes el código C# del ERP. La rama activa se ve en la barra inferior; debe coincidir con tu feature/ o fix/.

Roles (resumen)

Desarrollador

Crea ramas feature/ y fix/ y fusiona PRs en develop. Sin acceso a main ni qa.

Gestor / Aprobador

Desarrollador con permiso extra: además fusiona los PRs de develop a main (Wilmer, Marlon, Jorge, Víctor).

QA

Fusiona PRs en qa y prueba los cambios (Randy, Luis, Ronald). Sin acceso a develop ni main.

Pase Producción

Descarga main y publica el ERP. No necesita escribir en el repositorio.
